# Wellness Ledger

Wellness Ledger is a local educational prototype for exploring personal financial wellness. A signed-in user records monthly financial snapshots, gets an estimated wellness score (0-100) with an explanation, compares months, tracks savings goals, and tries temporary what-if scenarios.

## Features

- Login with username or Gmail address. Account recovery by email OTP (needs Gmail app-password environment variables).
- Monthly check-ins. Pick any month from the last 2 years to add or correct it.
- A score with a status band (Strong 75+, Moderate 50-74, At risk below 50).
- A rule-based reference score is calculated next to the model estimate. If the two differ by 12 points or more, the app warns the user.
- SHAP explanations show which factors moved the estimate most. Each factor is marked "On track" or "Needs attention" against a rule-of-thumb target.
- Personalised next steps, month-to-month comparisons, and a what-if simulator that does not change saved data.
- Savings goals with a "save about ₹X per month" hint, and a way to correct the saved amount.
- History page with a score chart, a CSV download of your check-ins, and delete-my-account.
- Guide page: how to use the app, what you get, and an "About your score" section with the limits.
- Light and dark mode toggle.

## Architecture

- `app.py` - Streamlit interface, input checks, charts, explanations, navigation, login lockout.
- `train_model.py` - synthetic data generation, feature engineering, rule-based target, model training and evaluation.
- `wellness_model.joblib` and `feature_columns.joblib` - model files created by `train_model.py`.
- `model_evaluation.json` - hold-out and cross-validation metrics created by `train_model.py`. The app does not read it. Use it for reports.
- `user_data.py` - SQLite storage for check-ins and goals. All SQL uses `?` placeholders. Connections are always closed.
- `auth.py` - local JSON account storage, salted password hashes, login, and email recovery.
- `wellness_ledger_data.db` - created locally at first run.
- `users.json` - created locally when accounts are registered.

## How to run

Use Python 3.11 or 3.12 in a virtual environment.

1. Install dependencies:

   ```bash
   python -m venv .venv
   # Windows:
   .venv\Scripts\activate
   python -m pip install -r requirements.txt
   ```

2. Create the model and its evaluation report:

   ```bash
   python train_model.py
   ```

3. Start the app:

   ```bash
   streamlit run app.py
   ```

If the model files are missing or from an older version, the app shows a message telling you to run step 2.

## Accounts and security

- Passwords need at least 8 characters. Usernames need 3-30 characters (letters, numbers, dot, dash or underscore).
- Passwords are salted and hashed (PBKDF2). Recovery OTPs expire after 10 minutes and allow 5 tries.
- Login lockout: 5 wrong attempts lock that username or Gmail for 5 minutes. The lockout is kept in memory, so it resets when the app restarts.
- Gmail ownership is not verified at sign-up.
- `users.json` has no multi-process file locking.

## Account recovery email (optional)

Set these environment variables before running Streamlit:

- `WL_EMAIL_ADDRESS` - the Gmail address used to send recovery messages.
- `WL_EMAIL_APP_PASSWORD` - a Google App Password, not the normal Gmail password.

You can demonstrate the app without account recovery. Test the email setup before any presentation.

## Data and privacy

Check-ins and goals are stored in the local SQLite database. Account details and password hashes are stored in `users.json`. Keep `users.json`, the database and any secrets out of public repositories and shared folders (both are listed in `.gitignore`). Users can download their check-ins or delete their account and all data from the bottom of the History page.

Back up local data before changing or deleting it. Use a separate demo account and demo data for presentations.

## How the score is made

1. **Data.** About 5,000 synthetic people. Their incomes, spending, savings and debts are generated by code. No real person's data is used.
2. **Ratios.** Rupee amounts become ratios: savings cushion (total savings divided by one year of income), debt-to-income, debt repayment burden, expense-to-income, emergency-fund months, discretionary share and income stability. In the code the savings cushion is called `savings_rate`.
3. **Rule-based reference score.** A transparent formula turns the ratios into 0-100 using common rules of thumb (6 months of savings, loan payments under 30% of income, expenses under 70%, 6 months of emergency money). Targets add up as 25 + 20 + 20 + 15 + 12 + 3 + 5 points.
4. **Model.** A Random Forest (300 trees, depth 8) is trained to predict that score from the ratios.
5. **Explanation.** SHAP shows how much each factor moved a prediction.
6. **Spending above income.** After the model predicts, the app caps the score at 49 ("At risk") if monthly spending is above income. This is a fixed rule applied after the model, not something the model learned.

Age and dependents are saved with each check-in but are not model inputs.

### Model results (hold-out test set of 1,000 synthetic people)

| Method | MAE | RMSE | R² |
|---|---|---|---|
| Rule-based formula | 2.01 | 2.51 | 0.968 |
| Gradient Boosting | 2.21 | 2.76 | 0.962 |
| **Random Forest (used)** | 2.61 | 3.32 | 0.945 |
| Linear Regression | 3.54 | 5.00 | 0.874 |
| Mean baseline | 11.30 | 14.10 | 0.000 |

Random Forest 5-fold cross-validation: R² 0.946 ± 0.002. Running `python train_model.py` again regenerates these numbers in `model_evaluation.json`.

**How to read this.** The labels come from a formula, and the model learns that formula. A high R² shows the model copies the rule well. The rule formula itself scores best, and Gradient Boosting scores higher than the Random Forest. The metrics do **not** show that the score predicts real-world financial outcomes.

## Limitations

- **Synthetic data.** The model has not seen real people. Synthetic examples may not represent students, irregular earners, households in severe distress, or all Indian financial situations.
- **Rule-based target.** The targets (20-30% limits, 6-month emergency fund) are rules of thumb, not laws.
- **Extreme cases.** The Random Forest can understate how bad an extreme case is (for example, very large debt). The app shows a warning when the model and the rule score differ by 12 points or more.
- **SHAP.** SHAP values describe how features contribute to the model's prediction compared with its training baseline. They do not show cause and effect and say nothing about a person's worth.
- **Not financial advice.** This is an educational decision-support prototype. Do not use it for credit, lending, eligibility or other high-stakes decisions.

## Before a demo

- Use a fake demo account with realistic sample figures.
- Delete old test data (for example any check-in for a very old month) or start with a fresh `wellness_ledger_data.db`.
- Do not expose a real `users.json` file or real account credentials.
- Run `python train_model.py` after changing feature engineering or the training target.
- Test the recovery email setup, or skip showing account recovery.
- Open the Guide page and say clearly that the score is based on synthetic data.
